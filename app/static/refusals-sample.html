Why the controls matter

A table of refusals proves nothing if it can be empty for the wrong reason, or full of things that are not refusals. So the run names the rows it expects and fails if one is missing or if either control shows up. A provider that fails is a failure, not a refusal: nobody decided anything. A decision that matched a rule is not a refusal either. Both are absent above, and the build breaks if that stops being true.

What this page does not claim

  • Every request and invoice id is invented. Nothing here is the live app's data, and the live refusal view is behind an admin token.
  • The run uses a local SQLite store and an in-memory event log. The event log is optional and is not switched on for this public deployment, so on the live app a draft the guard replaced would not appear in the view; it is shown here to show the shape.
  • It does not show the Postgres path, and it says nothing about how often any gate fires.
